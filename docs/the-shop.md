# The Shop application brief

The Shop gives an AV shop lead one operational worklist from prep through pack, load in and strike. Existing Gear Prep, Truck Pack Plan, Load In Plan and Strike Plan remain independently usable and retain their original browser data. This application takes explicit, reviewed copies of their records into its own plan; it never writes legacy keys.

The smallest useful flow is: name a plan, add work, copy a source plan or import its exported JSON, review the staged records, save, assign ownership and blockers, advance each record through the four phases, filter the queue, and export or restore a Shop backup. Import is a preview until confirmed. A failed or malformed import leaves the saved plan unchanged. The source name, source id and original record are retained on each copied row for provenance and lossless re-export.

`sbd.shop.v1` stores `{schema:'system-by-dave.shop.v1', name, items}`. Each item has an application id, title, case, department, owner, location, destination, notes, blocker, phase, status, optional requested/packed quantities, source and original. Save is explicit; failed storage writes retain the unsaved in-memory plan and offer JSON export. An existing invalid or future-version document is never overwritten; its original bytes can be exported for recovery. Restoring a valid Shop backup requires explicit confirmation, and Save first retains the unreadable bytes under a unique `sbd.shop.recovery.*` key. If that preservation write fails, Save refuses to replace the original. Legacy import keys are read only.

This slice excludes automatic two-way synchronization, gear inventory mutation, hardware control, and duplicate identity resolution across legacy plans. Copies from distinct tools remain distinct rows until the operator consolidates them. Gear Reference stays a separate read-only source. CueForge and PlotForge are maintained specialist products with separate ownership and no Shop data contract.

Acceptance: fresh add/edit/save/reload, import preview and cancel, malformed import recovery, original legacy key byte parity, export, desktop and phone keyboard operation, light/dark toggle, and no page scroll at 1440×900 and 375×812. The Rail owner must separately add `console:shop` route `/the-shop/`, context rules, offline assets and public navigation. Merge/deployment and live behavior require serialized integration.

The route remains `noindex` until the shared indexable-route registry and verifier count are updated during Rail integration.

## Gear Prep quantity and partial-pack slice

**Problem and outcome.** Gear Prep v1 saves and exports `items[].qty` as a numeric string, but The Shop currently keeps it only inside the retained original record. A shop lead cannot see the requested count or record a partial pack such as 1 of 3 while reconciling the worklist. This slice makes that count explicit without treating a legacy status as evidence of physically packed units.

**Flow.** Preview a saved Gear Prep plan or its exported JSON, see each requested quantity, then confirm a one-way copy. Review the copied row, explicitly enter the packed count, apply, Save, reload, export and restore. Cancel leaves both plans untouched. A repeated source row is rejected rather than duplicated; a saved-source preview becomes stale if that source changes before confirmation.

**Data and rules.** Keep `system-by-dave.shop.v1` and `sbd.shop.v1`. Add optional `requestedQty` and `packedQty` to Shop rows, each `null` (unknown) or a whole number from 0 to 99999. Gear Prep's blank or absent quantity maps to unknown; a nonblank malformed quantity rejects the entire preview. Other legacy tools and existing Shop backups without these fields load with unknown counts. Only an explicit operator entry sets `packedQty`; a missing value is not zero, and an imported `packed`/`loaded`/`ready` status never fills it. When both quantities are known, packed cannot exceed requested. Requested zero is retained as zero, not silently changed to unknown. Counts remain attached to the row when its phase/status changes; the label always says “Packed,” not phase completion. Neither count automatically changes status or clears a blocker. Original source objects, source identity and source storage bytes remain unchanged. An edit violating these rules leaves the working row unchanged. The existing explicit Save, damaged-document recovery and backup format remain compatible.

**Smallest useful slice and exclusions.** Show requested and packed quantities in the import preview, worklist and item inspector; allow explicit count edits; preserve the values in Shop JSON and recovery. This is not an inventory ledger, per-phase count system, automatic readiness verdict, two-way synchronization, duplicate reconciliation across distinct tools, producer change, Rail promotion, or full Stage 4 operator acceptance. It depends only on the existing Gear Prep v1 shape and Shop's current confirmed-copy flow.

**Risks and acceptance.** A partial count must not be mistaken for a full pack or a safety verdict. Test producer-shaped `qty:'3'` → requested 3 / packed unknown, then explicit packed 1 of 3 across Save/reload/export/restore; blank/zero/malformed quantities; old Shop backups; preview/cancel/confirm, repeated/stale source and malformed rejection; source-byte parity; keyboard/theme and viewport-locked phone/desktop layouts. CI, publication, live browser behavior and physical/operator acceptance are separate gates.

## Palette and operator preference

The Shop opts into the shared AV theme as `data-av-tool="the-shop"`, reads Warm Paper and Stage Slate tokens from `css/av-theme.css`, and applies the shared `av-theme-mode.v1` choice through `js/av-theme-mode.js`. Its visible toggle writes that shared choice. An older Shop-only light/dark choice is honored only when no shared preference exists; no legacy plan data is rewritten.
